# BOOST — 単体モデルをフロンティア級に引き上げるフレームワーク

**BOOST** は、Claude Code のセッションモデルが **Opus 4.8 単体**でも
**Sonnet 5 単体**でも、Fable 5(フロンティア級)に迫る成果を出すための
仕組みです。モデル自体は変わりません。変わるのは**仕事のさせ方**です。

## なぜ「構造」で差が埋まるのか

フロンティアモデルと単体モデルの差は、主に次の4点に現れます。
BOOST はそれぞれを構造で補償します。

| 単体モデルの弱点 | BOOST の補償 |
|---|---|
| 一発の計画の質が低い(最初の思いつきを深掘りしがち) | **複数の独立候補 + 審査員パネル**(`boost-judge-panel`)。異なるレンズで独立に設計させ、審査・合成する |
| 自分の成果物の欠陥を見つけられない(自分の推論を読み返すだけ) | **敵対的検証**(`boost-adversarial-review`)。フレッシュな文脈のレビュアー/懐疑者が反証投票し、定足数を満たした指摘だけ採用 |
| 長いタスクで文脈が崩れ、要求からドリフトする | **小さな作業パケット + 必須チェックポイント**(`/boost-plan` → `/boost-build`)。計画をファイルに書き、数ステップごとに要求を読み直す |
| 「動くはず」を「動いた」と報告してしまう | **証拠ゲート**(`/boost-verify`)。このセッションで観測した証拠(テスト出力・実行結果)がない主張は報告禁止 |

> **正直な期待値**: これはモデルの重みを変えるものではありません。
> 単発の短文問答のような「生の一発回答力」がそのまま上がるわけでは
> ないですが、実務のコーディングタスク(設計・実装・デバッグ・調査)では、
> 失敗の大半が「計画ミス・検証不足・ドリフト・過信」に由来するため、
> そこを構造で塞ぐことで体感品質はフロンティア級に近づきます。
> トークン消費は増えます(それが冗長性のコストです)。

## 構成ファイル

```
CLAUDE.md                                  ← 常時ロードされる規律(タスク分類・ハードゲート)
.claude/
  boost.config.json                        ← モデル別プロファイル(パラメータの一元管理)
  hooks/boost-profile.sh                   ← SessionStart でプロファイルを文脈に注入
  skills/
    boost/                                 ← ルーター: T0〜T3 分類と振り分け
    boost-plan/                            ← 計画: 要求整理→偵察→複数候補→批判→パケット分解
    boost-build/                           ← 実装: 1パケットずつ検証しながら進む
    boost-review/                          ← レビュー: 多レンズ + 反証で自己レビューの盲点を排除
    boost-verify/                          ← 証拠ゲート: 「完了」の定義と証拠基準
    boost-research/                        ← 調査: 多角スイープ + 主張の反証 + 二重導出
    boost-debug/                           ← デバッグ: 再現→仮説列挙→判別実験→根本原因証明
  agents/
    boost-scout.md                         ← 読み取り専用の偵察(文脈汚染防止)
    boost-planner.md                       ← 独立した計画候補の生成
    boost-critic.md                        ← 敵対的批評(具体的な失敗シナリオのみ)
    boost-builder.md                       ← 1パケット限定の実装
    boost-verifier.md                      ← 主張のゼロベース独立検証
  workflows/
    boost-judge-panel.js                   ← N候補生成→審査→合成
    boost-adversarial-review.js            ← レンズ別レビュー→反証投票
    boost-deep-research.js                 ← スイープ→蒸留→検証→合成
scripts/install-boost.sh                   ← 他リポジトリへのインストーラ
docs/BOOST.md                              ← このドキュメント
```

## チームモード(Fable 5 セッションの既定動作)

セッションモデルが **Fable 5** のとき(`activeProfile: "fable"` — 出荷時の
既定値)、アプリ/SaaS/機能開発の T2+ タスクは**役割別モデル分担**が
デフォルトになります:

| 役割 | モデル | 担当 |
|---|---|---|
| **計画・アイディア・意思決定** | Fable 5 | セッション本体。委譲しない(最高の推論力を要求・設計・統合判断に使う) |
| **実装** | Sonnet 5 | `boost-builder` エージェント(`model: "sonnet"`)が作業パケット単位で実装。独立パケットは並列実行 |
| **コードチェック** | Opus 4.8 | `boost-critic` / `boost-verifier`(`model: "opus"`)と `boost-adversarial-review`(`args.model: "opus"`)。**別の強いモデル**が見ることで同一モデル同士が共有する盲点を排除 |

ハードゲート(証拠なき完了報告の禁止など)は単体モードと完全に同一です。
指定モデルが使えない環境では、その役割だけセッションモデルに
フォールバックし、その旨を報告します(黙って段階をスキップしない)。
詳細は `.claude/skills/boost-team/SKILL.md`。

## プロファイル(モデル別チューニング)

`.claude/boost.config.json` の `activeProfile` を**セッションで使う
モデルに合わせて**設定します。`fable` はチームモード、`opus` / `sonnet`
は単体モード(そのモデルだけで完結)。単体モードはギャップが大きい
モデルほど冗長性を強くするのが原則です。

| パラメータ | `opus` (Opus 4.8) | `sonnet` (Sonnet 5) | 意味 |
|---|---|---|---|
| `planCandidates` | 2 | 3 | T2+ で生成する独立計画候補の数 |
| `judges` | 3 | 3 | 審査員パネルの人数 |
| `refuteVotes` | 2 | 3 | 指摘・主張ごとの独立反証投票数 |
| `surviveQuorum` | 2 | 2 | 「確定」に必要な支持票数 |
| `reviewLenses` | 4レンズ | 5レンズ(+requirements-coverage) | レビューの観点 |
| `maxUnverifiedSteps` | 2 | 1 | 検証なしで連続してよい編集ステップ数 |
| `researchAngles` | 3 | 4 | 調査の並列アングル数 |
| `doubleDerivation` | 重要主張のみ | 主要主張すべて | 独立ルートでの二重導出の範囲 |
| `hardStepEffort` | high | xhigh | 審査・批評・反証段階の推論努力(最終合成は常に xhigh) |

① **Opus 4.8 だけで使う** → `"activeProfile": "opus"`
② **Sonnet 5 だけで使う** → `"activeProfile": "sonnet"`
③ **Fable 5 で使う(既定)** → `"activeProfile": "fable"`(チームモード: 計画=Fable 5 / 実装=Sonnet 5 / チェック=Opus 4.8)

ワークフローとエージェントは**モデル指定を一切持たない**ため、常に
セッションモデルをそのまま継承します。「同じモデルの独立コンテキスト×
冗長性」が品質の源泉であり、裏でこっそり上位モデルを呼ぶことは
ありません(だから単体モデル縛りが守られます)。

なお、ワークフロースクリプトは設定ファイルを直接読めないため、
**呼び出すスキル側がプロファイル値を `args` で渡す**設計です
(各スキルに正確な呼び出しテンプレートを記載済み)。

## 動作の流れ

1. セッション開始時、`boost-profile.sh` フックが「BOOST 有効・プロファイル名」を文脈に注入。
2. `CLAUDE.md`(常時ロード)がタスクを **T0〜T3** に分類させる:
   - **T0**(自明): そのまま実行。儀式なし。
   - **T1**(小さな変更): インラインの 計画→実行→検証→セルフレビュー。
   - **T2**(複数ファイル・非自明): `/boost-plan` → `/boost-build` → `/boost-review` → `/boost-verify`。バグは `/boost-debug`、調査は `/boost-research`。
   - **T3**(アーキテクチャ・高リスク・徹底依頼): T2 + `boost-judge-panel` + `boost-adversarial-review` ワークフロー。
3. どの階層でも「観測した証拠なしに完了と言わない」「`maxUnverifiedSteps` を超えて未検証編集を続けない」等のハードゲートが適用(「初稿≠最終稿」と独立懐疑ゲートは T2+ が対象)。

手動で起動したい場合は `/boost`(ルーター)、あるいは各スキル
(`/boost-plan` など)を直接呼べます。ワークフローは
「`boost-judge-panel` ワークフローを実行して」のように依頼するか、
T3 タスクで自動的に使われます。

## 他リポジトリへのテンプレート展開

### 方法 A — インストーラ(推奨)

```bash
# 対象リポジトリに BOOST 一式をコピーし、CLAUDE.md とフックを配線
./scripts/install-boost.sh /path/to/target-repo          # プロファイルは既存/デフォルトを維持
./scripts/install-boost.sh /path/to/target-repo sonnet   # Sonnet 5 で使うリポジトリ
./scripts/install-boost.sh /path/to/target-repo opus     # Opus 4.8 で使うリポジトリ
```

- 何度実行しても安全(冪等)。CLAUDE.md はマーカー
  `<!-- BOOST:BEGIN/END -->` の間だけを更新するので、
  対象リポジトリ固有の記述は保持されます。
- 既存の `boost.config.json` は上書きしません(プロファイル引数を
  渡したときのみ `activeProfile` を書き換え)。
- `.claude/settings.json` が既にある場合は node で SessionStart フックを
  追記します(node がなければ手動追記の案内を表示)。

### 方法 B — GitHub テンプレートリポジトリ

このリポジトリ自体をテンプレート化(Settings → Template repository)
すれば、「Use this template」で BOOST 込みの新規リポジトリを作れます。
作成後に `activeProfile` をそのリポジトリで使うモデルに合わせるだけです。

### 方法 C — 既存の一括作成スクリプト

`scripts/bootstrap-repos.sh`(このリポジトリの全ファイルを引き継いで
連番リポジトリを作る)を使えば、BOOST も自動的に含まれます。

## カスタマイズ

- **厳しさの調整**: 品質最優先なら `refuteVotes` / `planCandidates` を
  増やす。トークンを節約したいなら T2 の既定をインラインモードに寄せる
  (ワークフローは T3 のみ)。数値は `boost.config.json` だけ触れば
  スキル側は追従します。
- **レンズの追加**: `reviewLenses` に `performance` を足すと
  `boost-adversarial-review.js` の組み込みレンズ定義が使われます。
  独自レンズ名も可(その場合は名前から意図が伝わるように)。
- **プロファイルの追加**: `profiles` に新しいキー(例: `haiku`)を足し、
  `activeProfile` で切り替え。ギャップが大きいほど
  `maxUnverifiedSteps` を小さく、票数と候補数を多く。

## FAQ

**Q. 遅くなりませんか?**
T0/T1 は素通しなので日常操作は変わりません。T2/T3 は明確に遅く・
高トークンになりますが、それは「手戻り・偽完了・見逃しバグ」と交換で
買っている品質です。`boost` ルーターにはオーバーキル防止ガードがあり、
途中で自明と判明したタスクは即座にダウングレードします。

**Q. Fable 5 と本当に同等になりますか?**
「同等を保証」ではなく「同じ失敗クラスを構造的に塞ぐ」が正確です。
計画・検証・レビューが支配的な実務タスクほど差は縮まり、
純粋な単発推論の切れ味そのものは対象外です。

実測例(2026-07、コードレビュー課題): 8個のバグを意図的に仕込んだ
SaaS課金モジュールを各条件でレビューさせ、正解キーで採点。

| 条件 | 発見 | 確定偽陽性 |
|---|---|---|
| Sonnet 5 素の一発レビュー | 7/8 | 0 |
| Opus 4.8 素の一発レビュー | 7/8 | 0 |
| Fable 5 素の一発レビュー(参照) | 7/8 | 0 |
| **Sonnet 5 + BOOST**(3レンズ+反証投票2名) | **8/8** | 0(投機的指摘3件を投票で排除、追加の真正指摘3件) |
| **Opus 4.8 + BOOST**(同上) | **8/8** | 0(重複指摘を投票で排除) |

素の一発では3モデルとも同じバグ(不明プランID→NaN)を見逃し、
BOOST のレンズ分割はどちらのモデルでもそれを捕捉——この課題では
**BOOST 適用の単体モデルが素の Fable 5 を上回りました**。
ただし n=1・レビュー課題1種の実測であり、全タスク種での同等性の
証明ではありません(それが上の回答の意味です)。

**Q. モデルを併用してもいい?**
構いません。BOOST はセッションモデルに依存しないので、Fable 5 で
使えばさらに上積みになります。プロファイルだけ合わせてください。
