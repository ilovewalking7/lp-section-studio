# 「109件の欠陥を直した」と書こうとしたら、その109という数字が間違っていた

> note 掲載用の原稿。公開前に「事実確認」の節のコマンドを実行して数字を照合すること。

---

2年かけて、UIコンポーネントを880個ためました。

React + TypeScript + Tailwind で、1ファイル1コンポーネント。ヒーロー、料金表、フッター、3Dカルーセル、和風テーマ、ブルータリズム。CIも回していて、テストは全部緑でした。

そのテストが見ていたのは、**「描画しても例外が出ないこと」だけ**でした。

そこに検査を4つ足したら、欠陥がぼろぼろ出てきました。全部、自分で書いて、自分で目視確認して、緑のCIを通してきたものです。その顛末を記事にしようとして、下書きにこう書きました。

> 結果、109件の欠陥が出てきました。

公開直前に内訳を並べ直したら、こうなりました。

```
コントラスト  12
axe          29
キーボード     0
横スクロール  26
```

**67です。** 109ではありません。どこから109が出てきたのか、自分でも分かりませんでした。ログを探しても出てこない。おそらく途中の作業ログのどれかの数字を、確認せずに書き写したのだと思います。

検査を入れて品質を語る記事で、その記事の数字が検算されていない。笑えないので、この話から始めることにしました。以下、67件が何だったのかという話と、**それを全部直した後で見つかった、もっと大きい1件**の話です。

---

## 足した検査

| 検査 | 何を見るか |
|---|---|
| コントラスト | デザイントークンの色を、WCAG の相対輝度で計算する |
| axe-core | 構造アクセシビリティ（名前のない要素、ARIAの誤用など） |
| キーボード | 対話部品にキーボードで到達できるか |
| 横スクロール | 実ブラウザ・幅375px で、ページが横に破れないか |

4つに分けたのには理由があります。**jsdom には描画エンジンが無いので、色も幅も測れない**からです。axe を jsdom で走らせても `color-contrast` ルールは動きません。だから色はトークン定義そのものを数値で計算し、幅は実ブラウザ（Chromium）で測る。役割を分けないと、検査したつもりの穴ができます。

以下、印象に残ったものを4つ。

---

### 1. コンポーネントが aria-label を握りつぶしていた

axe が `button-name` 違反を29件出しました。「ボタンに名前がない」——アイコンだけのボタンで、スクリーンリーダーが用途を読めない状態です。

そのうち13件が `<Switch>` でした。原因を見に行くと、こうなっていました。

```tsx
export interface SwitchProps {
  checked?: boolean;
  onCheckedChange?: (checked: boolean) => void;
  disabled?: boolean;
  className?: string;
  id?: string;
  // aria-label が無い
}
```

中身が空の `<button>` なので、名前は外から与えるしかありません。それができない設計でした。

ここからが本題です。**利用側のコードを見たら、こう書いてありました。**

```tsx
<Switch
  checked={annual}
  onCheckedChange={setAnnual}
  aria-label={en ? "Switch to annual billing" : "年額請求に切り替え"}
/>
```

**渡していたんです。**書いた本人（私）は正しくやろうとしていて、コンポーネント側が黙って捨てていた。

これは使用箇所をいくらレビューしても見つかりません。コードとしては完璧に見えるからです。実際に描画して、その結果を検査して初めて出てきました。

---

### 2. ひとつの色が、両立しない2つの仕事をしていた

コントラスト検査で12組の未達が出たので、明度を機械的に解いて直していきました。11組は素直に解けました。

**最後の1組だけが、どうやっても解けませんでした。**

```
[ダーク] NG 破壊的ボタンの文字 4.09:1（必要 4.5:1）
```

`--destructive`（赤）が、ダークモードで2つの役割を兼ねていました。

- **暗い背景の上のエラー文字** → 読ませるには明るくしたい
- **白文字を載せる削除ボタンの背景** → 白が読めるよう暗くしたい

同じ変数で、明るくも暗くもできません。**トークンの設計が間違っていた**という話で、値をいじって解決する問題ではありませんでした。

結局、ダークモードでは前景色のほうを暗色（`0 60% 7.3%`）に変えて両立させました。

この種の衝突は、測って初めて可視化されます。デザインツールの上で色を選んでいる限り、「この赤は2つの役割を持っている」とは気づけません。

---

### 3. 入場アニメーションが、ページを横に破っていた

横スクロール検査で26件が引っかかりました。3Dカルーセルが `overflow` を閉じ忘れている、といった予想通りのものが大半でしたが、2件だけ意外なものがありました。

```tsx
className={cn(
  "transition-all duration-700",
  shown ? "translate-x-0 opacity-100" : "translate-x-8 opacity-0"
)}
```

スクロールで滑り込んでくる、よくある演出です。**滑り込む前は、要素が右に32pxずれています。**

つまり画面に入る前の要素が、その間ずっと画面幅を超えている。実際のページでは、**読み込むたびに横スクロールバーが一瞬出て消えます。**

自分で何十回も見ていたはずの画面でした。一瞬すぎて、目では認識できていませんでした。

---

### 4. OFF のスイッチが、ほぼ見えていなかった

コントラスト検査が `--input` を叩きました。

```
[ライト] NG 入力欄の枠 1.27:1（必要 3:1）
```

WCAG 1.4.11 は「操作できる部品の境界」に 3:1 を要求します。入力欄の枠は「そこが入力欄である」ことを示す唯一の手がかりなので、対象です。1.27:1 では、ほぼ見えていません。

直すために `--input` を 90% → 60.3% に変えたのですが、**このトークンがもう1箇所で使われていました。**

```tsx
on ? "bg-primary" : "bg-input"   // スイッチのOFF時トラック
```

つまり**OFFのスイッチが、背景と 1.27:1 でほとんど見えていなかった**。入力欄の枠を直したら、そちらも同時に直りました。

## 全部直した。そして、もっと大きいのが出てきた

```
コントラスト  12 → 0
axe          29 → 0
キーボード     0 → 0
横スクロール  26 → 0
```

4つとも0。CIも緑。ここで満足して、配布用のZIPを作りはじめました。

このコンポーネント集には「React を使っていない人でも使えるように、静的HTMLとしても書き出せる」という売りがあります。880個のうち397個は状態を持たない純粋な表示部品なので、React 抜きのHTMLとして完成する。その書き出しHTMLを、念のため実ブラウザで開いて色を測りました。

```
bg-card の背景色              rgba(0, 0, 0, 0)   ← 透明
text-muted-foreground の文字色 rgb(0, 0, 0)       ← 真っ黒
```

**色が、出ていませんでした。**

書き出したHTMLは、Tailwind の CDN を1行読むだけの構成でした。

```html
<script src="https://cdn.tailwindcss.com"></script>
```

これで `flex` や `p-4` は効きます。でも `bg-card` や `text-muted-foreground` は**素の Tailwind には存在しません**。このプロジェクトが `tailwind.config.js` と `:root` の CSS 変数で定義した、独自のトークンだからです。CDN はそんな定義を知らない。だから何も生成されず、背景は透明のまま、文字は初期値の黒のままになる。

数えたら、**880個中430個**が該当しました。無料で配ろうとしていたMCP版100個のうち30個も、これに含まれていました。

4つの検査は、全部この欠陥を素通りしていました。当たり前です。検査していたのは**React コンポーネントとして描画した結果**であって、**書き出したHTML**ではなかったからです。アプリの中では `index.css` が読み込まれているので、トークンは全部解決する。検査は緑になる。書き出した先には、その `index.css` が付いていかない。

「検査を4つ入れて全部緑にしました」と胸を張った直後に、検査していない経路が丸ごと壊れていた。67件を直した話より、こっちのほうが教訓としては大きいと思います。

---

## 直し方

`wrapDocument()`（HTMLの外枠を作る関数）で、CDN の script の直後にトークン定義を差し込むようにしました。

```html
<script src="https://cdn.tailwindcss.com"></script>
<script>
  tailwind.config = { darkMode: "class", theme: { extend: { colors: { card: "hsl(var(--card))", ... } } } };
</script>
<style>
  :root { --card: 0 0% 100%; --muted-foreground: 240 3.8% 46.1%; ... }
  .dark { ... }
</style>
```

値は `tailwind.config.js` と `src/index.css` から生成しています。手で書き写すと、いつか必ずズレるからです。

直した後、同じ3件をもう一度ブラウザで測りました。

```
bg-card の背景色              rgba(0, 0, 0, 0) → rgb(255, 255, 255)
text-muted-foreground の文字色 rgb(0, 0, 0)     → rgb(113, 113, 122)
bg-muted の背景色             rgba(0, 0, 0, 0) → rgb(244, 244, 245)
```

880個すべてで注入を確認。HTMLは1件あたり3.7KB増えました。

ついでに、**この欠陥を再発させない検査**を足しました。配布ZIPを作るスクリプトが、トークン設定の入っていないHTMLを1件でも見つけたら、そこで止まって「`npm run html` を実行しろ」と言って終了します。中身のコピーを持たせず、「入っているかどうか」だけを見る検査です。

---

## 分かったこと

**検査は、検査した経路しか守らない。** これに尽きます。

4つの検査はどれも真面目に書いたもので、実際に67件を掘り出しました。でもそれは「Reactとして描画したとき」の話でした。同じコンポーネントが別の形（静的HTML）で出ていく経路があることを、検査の設計に入れ忘れていた。緑のCIは、その穴の存在を教えてくれません。むしろ「全部見た」という誤った安心をくれます。

もうひとつ。**配る前に、配る形のまま自分で開いてみる。** 今回それをやったのは半分偶然でした。ZIPの中身を確認していて、なんとなくブラウザにドラッグしただけです。やらなければ、色の出ないコンポーネント430個をそのまま出荷していました。

そして、この記事の書き出しに戻ります。109という数字も、検算せずに書いていました。**測ったつもり・数えたつもりが、いちばん危ない。**

## 事実確認

この記事の数字は、以下で再現できます。

```bash
node scripts/check-contrast.mjs   # コントラスト → 0件
npm test                          # axe / キーボード / 描画
node scripts/check-overflow.mjs   # 横スクロール → 0件
node scripts/build-release.mjs    # 配布物（トークン注入の検査を含む）
node scripts/verify-release.mjs   # 展開して実ブラウザで描画確認
```

導入時点の違反数（12 / 29 / 0 / 26）は、当時の記録がコード内のコメントに残っています（`src/registry/a11y.test.tsx` と `scripts/check-overflow.mjs` の冒頭）。
